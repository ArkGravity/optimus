# v0.1.2 repair and verified release

The user explicitly authorized fixing the v0.1.1 delivery errors, committing and
publishing a new v0.1.2 release, and comprehensively checking the published result.
This supersedes the previous request to skip CI/artifact review. Existing
published v0.1.0/v0.1.1 tags, releases, images and attachments must remain intact.
No Production deployment or application database operation is authorized.

## Repair

- Update the RBAC menu contract test from the retired `k8s` group to `containers`
  and assert the Kubernetes/Docker children and permissions.
- Compare the persisted custom-grant timestamp before and after seed. Use an
  explicit nanosecond timestamp fixture so database precision loss is exercised
  on every platform without weakening the grant-preservation assertion.
- Add versioned release notes, upgrade instructions and a truthful changelog.
  Retain the existing release eligibility checks and native artifact pipeline.

## Delivery and checks

1. Reproduce the affected failures and run the corrected seed/RBAC database race
   suites against a dedicated disposable PostgreSQL 17 instance on Colima.
2. Commit/push the repair and notes; wait for all six exact-main CI jobs,
   including actual database tests, Docker build and dual-registry publication.
3. Create one annotated v0.1.2 tag on that source, then let the release workflow
   build/test native Linux amd64 and arm64 artifacts and produce a draft.
4. Download the exact six draft attachments independently. Check filenames,
   checksums, archive contents, version/config/license/installation contracts,
   and equality of archive binaries to the workflow's tested saved images.
5. Inspect GHCR and Docker Hub anonymously: both architectures, matching index,
   platform and configuration digests, source/version labels, and IMAGES.txt.
6. Publish only the verified draft, as already authorized by the user. Recheck
   public release metadata, original asset IDs/checksums and anonymous registry
   reads after publication. Record evidence and clean owned test resources.

Status: formally published and independently verified; final evidence below.

- Both original failures reproduced against the dedicated PostgreSQL 17
  container. The explicit nanosecond fixture also reproduced the timestamp
  assertion failure on macOS, so this regression no longer depends on host
  clock precision.
- Corrected seed/RBAC database race suites passed all 35 tests with
  `-tags=dbtest -race -count=1`; focused tagged Go lint and diff checks passed.
- Local verification uses only the task-owned `optimus-v012-tests-20261112`
  container on its independently assigned loopback port. The existing
  `optimus-dev-postgres-1`, its volume and all shared Kubernetes resources are
  outside this task's cleanup scope. The pre-existing postgres:17-alpine image
  must also be preserved.

The first repair commit `0f3143b` reached exact-main CI `43299650267`. Its two
original regressions passed, but the full database suite exposed the existing
`TestCache_RespectsTTL` timing assumption: CI database writes exceeded its 50ms
TTL, so the cached-read assertion naturally observed refreshed permissions.
The follow-up uses a test-only expiry helper, retains both cache-hit and
post-expiry reload assertions, and removes the real sleep. Production cache
code/API and TTL behavior remain unchanged. That failure required the new exact-main run recorded below.
The deterministic TTL regression passed five consecutive race-enabled database
runs locally; focused tagged RBAC lint passed. The original run's Docker build
also passed, while image publication was correctly skipped after database failure.
